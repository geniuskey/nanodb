# NANoDB Core Business Logic Model

## 범위

이 설계는 US-01~US-07의 P0 흐름만 다룬다. 저장 기술과 프레임워크가 아니라 입력, 판단, 변환, 결과와 실패 조건을 정의한다.

## 1. 데모 상태 준비

1. 승인된 sample manifest와 PNG/JPEG 파일을 읽는다.
2. 파일 존재, 실제 이미지 decoding, 지원 형식, 픽셀 크기, 양수 보정값과 manifest 필수값을 확인한다.
3. TIFF 원천을 사용했다면 원천 ID, SHA-256, 변환 시각과 픽셀 크기 보존 여부를 확인한다.
4. 전용 demo database와 runtime upload만 알려진 초기 상태로 되돌린다.
5. 원천 sample은 수정하거나 삭제하지 않는다.
6. 사전점검 실패 시 데모 준비 완료로 표시하지 않고 실패 항목을 남긴다.

## 2. 이미지 등록

### 입력

- 이미지 파일 한 개
- `SEM` 또는 `TEM`
- Product, Lot, Wafer 식별 문자열
- 양수인 `nm/pixel` 보정값

### 처리

1. 모든 필수 입력의 존재 여부를 확인한다.
2. 20MB 이하인지, 확장자가 아니라 실제 decoding 결과가 PNG/JPEG인지 확인한다.
3. decoding 결과에서 원본 픽셀 너비와 높이를 얻는다.
4. 사용자 파일명과 무관한 내부 저장 키를 만든다.
5. 파일과 Image record를 저장한다. 둘 중 하나라도 실패하면 조회 가능한 Image로 성공 처리하지 않는다.
6. 저장된 Image view를 반환한다.

### 결과

- 성공: 새 이미지의 측정 화면으로 이동할 수 있는 Image view
- 실패: 사용자가 수정 가능한 입력 오류 또는 일반 저장 실패

## 3. 이미지 목록·상세와 요약

- 목록은 Image `created_at` 내림차순으로 정렬한다.
- 각 목록 항목에 원본 파일명, 종류, 제조 식별정보와 저장 측정 수를 결합한다.
- 상세는 Image와 연결된 Measurement 목록을 함께 제공한다.
- Measurement 목록은 `created_at` 내림차순이며 동일 시각이면 ID로 순서를 고정한다.
- 요약은 현재 저장된 전체 Image 수와 Measurement 수, 계산 기준 시각을 반환한다.
- 데이터가 없으면 0과 명시적 빈 상태를 반환하고 예시값을 만들지 않는다.

## 4. 두 점 측정

### 클라이언트 준비

1. 사용자가 `CD`, `Depth`, `Thickness` 중 하나를 선택한다.
2. 화면 클릭 좌표를 실제 표시된 이미지 영역 기준으로 정규화한다.
3. 원본 픽셀 좌표로 변환하고 이미지 영역 안인지 확인한다.
4. 두 점이 준비되면 선, 픽셀 거리와 예상 nm 값을 표시한다.
5. 초기화 시 아직 저장하지 않은 두 점, 선과 계산 표시를 제거한다.

### 서버 기준 계산

1. Image 존재 여부와 저장된 픽셀 크기·보정값을 읽는다.
2. 항목과 두 점의 좌표가 유효하고 서로 다른지 확인한다.
3. `distance_px = sqrt((end_x - start_x)^2 + (end_y - start_y)^2)`를 계산한다.
4. `value_nm = distance_px * calibration_nm_per_pixel`을 계산한다.
5. 두 결과가 유한한 양수인지 확인한다.
6. 서버 계산값, 사용한 보정값, 선택 메모와 생성 시각을 Measurement로 저장한다.
7. 저장 결과를 반환하고 UI 목록과 overlay에 즉시 반영한다.

클라이언트가 보낸 거리나 nm 값은 저장 기준으로 신뢰하지 않는다.

## 5. 측정 복원

1. 상세 조회에서 저장된 원본 좌표와 계산값을 읽는다.
2. 현재 표시 이미지의 실제 rendering 영역을 계산한다.
3. 원본 좌표를 rendering 좌표로 변환해 선과 끝점을 그린다.
4. 선택된 Measurement의 선과 목록 항목에 같은 강조 상태를 적용한다.
5. 값은 소수점 둘째 자리로 표시하되 저장값을 변경하지 않는다.
6. 화면 크기 변경이나 새로고침 후에도 원본 좌표에서 다시 계산해 overlay를 복원한다.

## 6. 개발 컨텍스트 내보내기

1. 대상 Image와 저장 Measurement가 한 건 이상 존재하는지 확인한다.
2. Image와 그 Image의 모든 Measurement를 하나의 논리적 snapshot으로 읽는다.
3. 모든 좌표, 보정값, 거리와 nm 값이 내보내기 계약에 유효한지 다시 확인한다.
4. Measurement를 ID 오름차순으로 정렬한다.
5. 같은 snapshot에서 다음 UTF-8 파일을 만든다.
   - `context.md`: field 계약, 좌표계, 계산식, 수동·미검토 상태
   - `data.json`: schema version, 시각, Image와 Measurements
   - `task.md`: 항목별 요약 CSV 생성 요청
   - `checks.json`: 기대 집계, 허용 오차와 독립 합성 계산 사례
6. 고정 파일명만 사용해 ZIP을 생성한다.
7. ZIP 다운로드를 반환하며 저장된 Image와 Measurement는 변경하지 않는다.

존재하지 않는 Image, 측정 없음, 유효하지 않은 snapshot 또는 생성 실패는 성공 ZIP으로 반환하지 않는다.

## 7. 외부 AI 개발 검증

1. 사용자가 ZIP을 앱 밖의 기존 AI 도구에 수동으로 전달한다.
2. 생성 코드를 검토한 뒤 로컬에서 실행한다.
3. CSV header, row order, count와 평균을 `checks.json`과 비교한다.
4. prompt, 입력 version, 모델 정보, 실행 명령, 시각과 실제 통과·실패를 근거로 남긴다.
5. 수작업 설명과 context 사용의 준비 시간·추가 요청 수·검증 결과를 같은 과제로 기록한다.

이 활동은 Core runtime 기능이 아니며 실패 또는 미실행 상태도 그대로 보존한다.

## 실패 처리 원칙

| 실패 유형 | 결과 |
| --- | --- |
| 누락·형식·범위 오류 | 저장하지 않고 수정 가능한 메시지를 제공한다. |
| 대상 Image 없음 | 찾을 수 없음으로 처리한다. |
| 파일 또는 database 저장 실패 | 성공 상태를 만들지 않고 일반 오류를 제공한다. |
| Measurement 계산 오류 | 저장하지 않고 입력을 유지해 수정할 수 있게 한다. |
| Export 계약 오류 | ZIP을 제공하지 않고 이유를 표시한다. |
| 예상하지 못한 오류 | 내부 상세정보를 숨기고 실패 사실과 재시도 가능한 행동만 표시한다. |
