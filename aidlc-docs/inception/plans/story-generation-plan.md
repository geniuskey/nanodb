# NANoDB User Stories 생성 계획

## 목적

승인된 3일 MVP 요구사항을 사용자 중심의 작고 시험 가능한 이야기로 변환한다. 현재 구현 범위, 앱 밖 AI 개발 검증과 평가 자료를 구분하고 각 이야기에서 관련 요구사항과 인수 조건을 추적한다.

- [x] 가능한 이야기 분해 방식과 상황별 질문을 준비한다.
- [x] 질문 수, 빈 답변 태그, 기타 선택지, 로컬 링크와 Markdown 공백을 검증한다.
- [x] 아래 모든 `[Answer]:` 태그의 답변을 수집한다.
- [x] 답변의 누락, 모호성 및 상충 여부를 분석한다.

- [x] 사용자의 자율 작성 지시를 해커톤 최소 계획의 명시적 승인으로 기록한다.

## 이야기 분해 선택지

| 방식 | 장점 | 이 프로젝트에서의 주의점 |
| --- | --- | --- |
| 사용자 여정 기반 | 등록부터 외부 검증까지 실제 시연 순서를 보존한다. | 홈·오류·평가 근거 같은 횡단 관심사가 여러 여정에 걸칠 수 있다. |
| 기능 기반 | 요구사항 ID와 구현 기능을 직접 대응하기 쉽다. | 사용자 가치보다 화면이나 모듈 중심으로 보일 수 있다. |
| 페르소나 기반 | 측정 사용자, 개발자와 평가자의 목적 차이를 명확히 한다. | 한 로컬 사용자가 여러 역할을 겸하는 MVP 전제와 중복될 수 있다. |

## 자율 결정 기록

사용자가 해커톤용으로 간결하게 작성하도록 위임했으므로 다음 기준을 적용했다.

- 현재 MVP의 로컬 사용자와 평가자만 다룬다.
- `Image → Measurement → Development Context → 외부 검증` 여정을 중심으로 한다.
- 화면 또는 데모 단계 단위로 묶고 체크리스트형 인수 조건을 사용한다.
- P1과 장기 로드맵은 이번 이야기에서 제외한다.
- 평가자는 소개와 근거를 빠르게 확인하는 읽기 여정만 다룬다.

답변 간 모호성이나 충돌은 없다. 사용자의 `네가 알아서 작성해줘` 지시를 위 기준의 선택과 계획 실행에 대한 명시적 승인으로 기록한다.

## 범위 보호 원칙

- 앱 내 AI 호출, 생성 코드 자동 실행과 다른 네 프로젝트의 기능은 만들지 않는다.
- P0 계측 기반과 P0 개발 지원을 모두 현재 MVP로 유지한다.
- 수동 측정은 미검토 참고값이며 자동 경계 판별이나 인증된 정답으로 표현하지 않는다.
- 기능 완료, 외부 AI 개발 데모 실행과 정적 사이트 게시 상태를 서로 구분한다.
- 구현 방법, 기술 스택과 일정 상세는 후속 Workflow Planning 및 설계 단계에서 결정한다.
