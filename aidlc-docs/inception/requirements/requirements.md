# NANoDB 제품 비전 및 MVP 요구사항 분석

## 문서 구조와 범위

이 문서는 NANoDB의 장기 제품 비전과 3일 해커톤 MVP의 범위를 정의한다. 다섯 명은 각자 소속 팀에 필요한 도구를 독립 개발하며, NANoDB 담당자는 자신의 앱·데이터·검증·문서를 책임진다. 다른 네 명의 NANoDB 지원을 전제하지 않는다.

2026-09-08 사용자 승인 방향: 반도체 이미지와 측정 근거를 AI 분석 소프트웨어 개발의 컨텍스트와 검증 데이터로 재사용한다. 이번 변경은 요구사항 수정이며 앱 기능이 구현됐다는 뜻은 아니다.

- **Part I**은 개발 단계 반도체 이미지·계측 데이터가 해결해야 할 문제와 장기 제품 방향을 설명한다.
- **Part II**는 현재 MVP에서 실제로 구현하고 검증할 기능을 한정한다.
- Part I의 기능이 Part II에 명시되지 않았거나 Part II의 제외 범위에 있으면 후속 로드맵으로 해석한다.
- 제품 비전과 MVP 범위가 충돌할 때는 Part II의 제약과 제외 범위를 현재 구현 기준으로 우선한다.

## Part I. Project Vision and Problem Statement

### 1. Business Context

반도체 양산 단계의 SEM 계측은 측정 대상 구조와 구조 파라미터가 이미 정의되어 있고, 동일한 형태의 제품을 반복적으로 측정한다.

측정 위치, CD 정의, 측정 방법, 장비 recipe 및 판정 기준이 비교적 안정적이기 때문에 자동 길이 측정과 데이터베이스 관리가 가능하다. 측정 결과도 Product, Lot, Wafer 및 공정 정보와 연결되어 체계적으로 축적된다.

반면 반도체 개발 단계에서 생성되는 SEM, TEM 및 Layout 이미지는 성격이 다르다.

개발 과정에서는 구조, 형상, 재질, 공정 조건과 관찰 목적이 실험마다 달라진다. 아직 설계가 확정되지 않았기 때문에 같은 이름의 구조도 형태나 측정 기준이 달라질 수 있으며, 새로운 구조 파라미터가 실험 도중 정의되기도 한다.

특히 TEM 분석은 시편 제작, 관심 구조 식별, 경계 판정 및 측정 과정에 전문가의 해석이 필요하다. 완전 자동화가 어렵고 분석자가 이미지 위에서 직접 길이와 형상을 확인하는 경우가 많다.

### 2. Problem Statement

개발 단계의 SEM/TEM 분석 데이터에는 다음 문제가 있다.

#### 2.1 데이터의 비정형성

개발 중인 구조는 반복 생산을 전제로 한 고정 schema를 갖지 않는다.

- 실험마다 구조와 재질이 달라진다.
- 관찰 대상과 측정 위치가 달라진다.
- 기존에 없던 파라미터가 새로 정의된다.
- 동일 파라미터 이름도 개발 시점이나 담당자에 따라 의미가 다를 수 있다.
- 구조 파라미터의 정의가 설계 변경과 함께 바뀔 수 있다.

따라서 양산 계측 시스템처럼 미리 고정된 측정 항목과 database schema를 적용하기 어렵다.

#### 2.2 이미지와 측정값의 분리

개발 단계의 측정은 이미지 위에서 수동으로 이루어지지만, 결과는 주로 PowerPoint나 Excel에 기록된다. 이 과정에서 다음 정보가 분리되거나 유실된다.

- 측정값이 산출된 원본 이미지
- 이미지상의 실제 측정 위치
- 측정에 사용한 선분, 경계 또는 관심 영역
- Scale bar 및 calibration 조건
- 구조와 파라미터의 당시 정의
- 측정자와 측정 시점
- Product, Lot, Wafer, Die 및 시편 정보
- 측정값의 수정과 검토 이력

숫자만 남고 측정 근거가 사라지기 때문에 결과를 다시 검증하거나 재사용하기 어렵다.

#### 2.3 분석 결과의 고립

PowerPoint와 Excel 중심의 데이터는 개별 분석 업무를 완료하는 데는 유용하지만, 조직 단위의 데이터 자산으로 축적되기 어렵다.

- 이전에 측정한 유사 구조를 찾기 어렵다.
- 동일 Product 또는 구조 파라미터의 산포를 즉시 계산할 수 없다.
- 서로 다른 실험과 시편의 결과를 일관된 기준으로 비교하기 어렵다.
- 이상값에서 원본 이미지와 측정 위치로 역추적하기 어렵다.
- 분석자의 개인 자료가 후속 개발에 재사용되지 못한다.
- 자동 측정 알고리즘을 개발할 검증 데이터가 축적되지 않는다.

#### 2.4 개발 데이터의 불확실성

개발 단계의 이미지는 전체 Product, Lot 또는 Wafer를 대표하지 않을 수 있다.

특히 TEM은 제한된 위치에서 제작한 소수 시편을 관찰하므로, 하나의 시편에서 얻은 여러 측정값을 여러 독립 표본처럼 해석하면 잘못된 결론에 이를 수 있다.

플랫폼은 단순히 측정값을 저장하는 것을 넘어 다음 정보를 함께 보존해야 한다.

- 어느 Wafer와 Die에서 가져온 시편인지
- 어떤 위치와 방향을 관찰했는지
- 하나의 시편에서 몇 개의 측정값을 얻었는지
- 측정 대상의 경계가 얼마나 명확했는지
- 수동 측정인지 자동 측정인지
- 결과가 검토되고 승인되었는지

#### 2.5 AI 분석 코드 개발의 반복 설명

AI로 분석 스크립트를 만들 때 이미지·측정 데이터의 필드 의미, 좌표계, 단위, 보정값과 기대 결과를 반복 설명해야 한다는 문제를 검증 가설로 둔다. NANoDB는 축적된 측정 근거를 개발 컨텍스트로 내보내 이 준비 비용과 해석 오류를 줄일 수 있는지 관찰한다.

### 3. Product Purpose

이 프로젝트의 목적은 개발 단계에서 생성되는 SEM, TEM 및 Layout 이미지와 구조 파라미터를 하나의 추적 가능한 데이터 모델로 통합하는 것이다.

플랫폼은 구조가 계속 변경되는 개발 환경을 수용할 수 있도록, 고정된 측정 schema를 강제하기보다 다음 요소를 유연하게 정의하고 버전 관리한다.

- 구조
- 재질과 Layer
- 구조 파라미터
- 측정 방법
- 측정 단위
- 이미지상의 측정 geometry
- 파라미터 정의와 적용 범위

사용자는 SEM/TEM/Layout 이미지를 등록하고, 이미지 위에서 구조와 관심 영역을 지정하며, CD, Depth, Thickness, Pitch, Curvature 및 Roughness 등의 파라미터를 측정할 수 있어야 한다.

수동 측정 결과와 영상처리 기반 자동 측정 결과는 모두 원본 이미지 및 측정 geometry와 연결되어야 한다.

### 4. Core Product Concept

플랫폼의 핵심 데이터 연결은 다음과 같다.

`개발 대상 → 제조 추적성 → Layout 구조 → SEM/TEM 관찰 이미지 → 구조 정의 → Annotation → 측정값`

각 측정값은 다음 질문에 답할 수 있어야 한다.

- 무엇을 측정했는가?
- 구조 파라미터는 당시 어떻게 정의되어 있었는가?
- 어느 Product, Lot, Wafer, Die 및 시편에서 나온 결과인가?
- 어떤 이미지의 어느 위치에서 측정했는가?
- 어떤 calibration과 측정 방법을 사용했는가?
- 수동 측정인가, 영상처리 결과인가?
- 누가 측정하고 누가 검토했는가?
- 이후 파라미터 정의나 측정값이 어떻게 변경되었는가?

### 5. Layout, SEM and TEM Integration

Layout 이미지는 설계 의도를 나타내고, SEM/TEM 이미지는 실제 제작된 구조의 관찰 결과를 나타낸다.

플랫폼은 이 세 종류의 이미지를 독립된 파일로만 저장하지 않고 서로 연결할 수 있어야 한다.

- Layout 영역과 SEM/TEM 관찰 위치 연결
- 설계 구조와 실제 관찰 구조 비교
- 동일 구조의 서로 다른 공정 조건 및 시편 비교
- Layout에서 정의한 nominal dimension과 측정값 비교
- 저배율 이미지와 고배율 이미지 연결
- 동일 시편에서 생성된 여러 TEM 이미지 연결

초기 제품 단계에서는 정확한 image registration이나 좌표 자동 정합을 필수로 하지 않는다. 관련 이미지와 구조 영역을 사용자가 수동으로 연결하는 기능부터 제공한다. 단, 현재 3일 MVP에서는 Layout 연계와 이미지 간 연결을 구현하지 않고 후속 로드맵으로 둔다.

### 6. Flexible Structure Parameter Model

개발 단계에서는 구조 파라미터가 사전에 완전히 결정되지 않는다.

따라서 플랫폼은 관리자만 고정 schema를 수정하는 방식이 아니라, 측정자가 새로운 파라미터 후보를 제안하고 분석가가 검토한 후 공식 정의로 승격할 수 있어야 한다.

구조 파라미터는 최소 다음 상태를 가진다.

- `proposed`: 특정 실험을 위해 임시로 제안된 정의
- `active`: 검토 후 재사용 가능한 공식 정의
- `deprecated`: 새로운 정의로 대체된 과거 정의

각 파라미터 정의에는 다음 정보를 저장한다.

- Parameter code와 이름
- 설명
- 대상 구조와 재질
- 측정 기준점과 방향
- Annotation geometry
- 단위
- 계산 방식
- 적용 가능한 Product 또는 실험 범위
- 정의 version
- 작성자와 승인자
- 변경 사유

정의가 변경되더라도 과거 측정값은 당시 사용된 파라미터 version과 연결되어야 한다. 현재 3일 MVP는 CD, Depth, Thickness의 고정 선택지만 제공하며, 사용자 정의 파라미터의 제안·검토·버전 관리는 후속 로드맵으로 둔다.

### 7. Target Users

#### 측정자

SEM/TEM/Layout 이미지를 등록하고 구조를 식별하며, 이미지 위에서 수동 또는 반자동 측정을 수행한다. 기존에 PowerPoint와 Excel에서 수행하던 측정 기록을 플랫폼에 직접 축적한다.

#### 분석가

측정 결과와 구조 파라미터 정의를 검토하고, Product, Lot, Wafer, 시편 및 실험 조건별 산포를 분석한다. 이상값에서 원본 이미지와 측정 위치까지 역추적한다.

#### 분석 소프트웨어 개발자

선택한 이미지와 측정의 데이터 계약·예시·개발 요청 템플릿을 내보내 기존 AI 도구로 분석 스크립트를 개발하고, 독립 기준 사례와 저장 데이터로 결과를 확인한다.

#### 시스템 관리자

사용자와 권한, 표준 단위, 장비, Product 및 구조 파라미터 정의를 관리한다. 데이터 품질과 보존 정책, API 접근 및 감사 이력을 관리한다.

현재 3일 MVP는 인증과 역할별 권한을 구현하지 않으며, 한 로컬 사용자가 측정자와 분석 소프트웨어 개발자 흐름을 함께 시연할 수 있다.

### 8. Expected Outcomes

플랫폼 도입을 통해 다음 상태를 달성한다.

1. 개발 SEM/TEM 측정 결과가 개인 PowerPoint와 Excel에 고립되지 않는다.
2. 모든 측정값을 원본 이미지와 측정 위치까지 역추적할 수 있다.
3. 아직 확정되지 않은 구조 파라미터도 임시 정의와 version을 통해 관리할 수 있다.
4. SEM, TEM 및 Layout 이미지를 동일한 개발 구조와 연결할 수 있다.
5. 같은 Product와 구조 파라미터의 측정값을 모아 산포를 분석할 수 있다.
6. 측정 방법과 파라미터 정의가 변경되어도 과거 데이터의 의미가 보존된다.
7. 반복적인 길이 측정은 간단한 영상처리로 보조하고 사용자가 결과를 검증할 수 있다.
8. 장기적으로 자동 측정 및 이미지 분석 기술을 개발할 수 있는 검증 데이터를 확보한다.

현재 MVP는 원본 이미지·측정 위치·측정값의 연결을 먼저 검증하고, 개발 컨텍스트 내보내기와 AI 생성 분석 코드 검증까지 연결한다.

### 9. Product Positioning

이 플랫폼은 양산 SEM 계측 시스템을 대체하기 위한 제품이 아니다.

양산 시스템이 확정된 구조의 반복 측정과 공정 관리를 담당한다면, 이 플랫폼은 구조와 측정 기준이 계속 변하는 개발 단계의 이미지 및 측정 데이터를 체계화하는 역할을 담당한다.

즉, 이 플랫폼의 핵심 가치는 완전 자동화가 아니라 다음에 있다.

> 아직 표준화되지 않은 개발 데이터를 측정 근거와 함께 축적하여, 이후 검색·비교·재현·분석 및 자동화가 가능한 데이터로 전환하는 것.

### 10. Success Indicators

- PowerPoint와 Excel 외부에서 재사용 가능한 측정값의 비율
- 원본 이미지와 측정 annotation까지 완전히 추적 가능한 측정값의 비율
- 기존 자료 검색 대비 유사 구조 및 측정 결과 검색 시간 감소
- 구조 파라미터별 Product/Lot/Wafer 산포 분석 준비 시간 감소
- 재측정 없이 기존 결과를 재사용한 횟수
- Proposed 파라미터가 검토 후 재사용 가능한 정의로 전환된 비율
- 반자동 측정을 통한 평균 측정 시간 감소
- 자동 측정 결과의 사용자 수정률과 승인률

이 지표들은 장기 제품 성과 지표다. 현재 MVP에서는 등록 건수와 좌표 복원, 개발 컨텍스트 계약 및 AI 생성 코드 검증을 확인한다. 설명 자료 준비 시간, 추가 설명·수정 요청 수와 검증 통과 수를 비교 관찰하며 개선을 보장하지 않는다.

## Part II. 3일 MVP 요구사항

### 1. 의도 분석

- **사용자 요청**: 대회 취지와 각자 실무 도구를 만드는 목표를 함께 반영한다. NANoDB의 계측 자산을 AI 분석 소프트웨어 개발 컨텍스트와 검증 데이터로 재사용하고 5명·3일 독립 개발 전제로 수정한다.
- **요청 유형**: 기존 요구사항 보강
- **범위 추정**: 제품 비전, 홈 탭, MVP 공통 요구사항, 구현 제외사항에 걸친 문서 변경
- **복잡도**: 보통 — 기능 자체는 작지만 3일 타임박스, 원천/데모 형식 분리와 재현 가능한 검증이 필요함
- **분석 깊이**: 표준
- **핵심 제약**: NANoDB 담당자 한 명의 3일 범위에서 계측 기반, 개발 컨텍스트 내보내기, 외부 AI 개발 검증과 최소 평가 자료를 준비한다. 다른 프로젝트의 기능 통합은 요구하지 않는다.

### 4. 기능 요구사항 요약

#### 4.1 홈과 내비게이션

- `/`에서 홈을 제공한다.
- NANoDB 로고, 확장명 `Nano Assets, Never orphaned Database`, 부제 `데이터는 쌓이고, 툴은 이어진다.`, 실제 이미지·측정 수와 기준 시각을 표시한다.
- 홈, 이미지 목록, 이미지 등록을 실제 동작 메뉴로 제공한다.
- 미구현 제품 메뉴를 노출하면 `준비 중` 또는 `P2`로 표시하고 클릭을 제공하지 않는다.

#### 4.2 홈 본문과 CTA

- 소개 영상, 대의와 세 가지 가치, 실측 KPI, 최근 등록 이미지, Phase 1~4, AI-DLC, 사용 흐름과 짧은 정책 줄을 유지한다.
- 홈 본문은 읽는 문서로 유지하고 화면 이동은 상단 내비게이션이 담당한다. 예외로 `이렇게 쓰세요` 사용 흐름 섹션 끝에만 `이미지 등록`·`이미지 둘러보기` CTA 두 개를 둔다.
- Tool 등록과 API/Skill 호출은 활성 CTA로 제공하지 않는다.
- 홈 화면의 정본은 `home-tab-requirements.md`이며, 이 문서와 MVP 문서 5.2절은 요약만 유지한다.

#### 4.3 실제 KPI

- 전체 이미지 수와 전체 측정 수를 PostgreSQL 데이터에서 계산한다.
- P1으로 항목별 측정 평균을 제공할 경우 단위 `nm`와 표본 수 `n`을 표시한다.
- 집계 기준 시각을 표시한다.
- 빈 데이터에서는 0 또는 측정 없음을 표시한다.
- PDF 예시값, 라벨 완료율, Tool 생존율은 실제 KPI로 표시하지 않는다.

#### 4.4 핵심 데모 기능

- PNG/JPEG/TIFF SEM/TEM 이미지와 Product, Lot, Wafer, `nm/pixel`을 등록한다. TIFF는 원본을 보존한 채 원본 픽셀 크기를 유지한 PNG 파생본을 만들어 화면에 표시한다.
- 목록에서 이미지를 찾고 다시 연다. 단일 검색어와 SEM/TEM 필터를 제공한다(구현 완료).
- 원본 이미지 기준 두 점 좌표로 CD, Depth, Thickness를 측정한다. 측정 화면에는 보정값, 원본 픽셀 크기와 현재 배율의 지정 가능 정확도를 함께 표시한다.
- 측정을 저장할 때 그 측정이 무엇인지 나타내는 라벨을 함께 남기고, 라벨은 자기 측정선 옆에 캡션으로 표시한다. 공정 Step은 이미지 등록 시 한 번만 입력한다.
- 계산된 측정값과 좌표를 저장·복원·선택한다. 측정과 이미지 삭제를 제공하며, 저장 측정은 라벨과 메모만 수정할 수 있고 좌표·항목·값은 불변이다.
- 원본 파일은 수정하지 않고 측정을 별도 파생 데이터로 저장한다.
- 각 측정값은 최소한 원본 이미지, 두 점 좌표, 파라미터 종류, 보정값, 단위와 생성 시각까지 역추적할 수 있어야 한다.

#### 4.5 데모 데이터 준비

- 브라우저가 직접 등록할 수 있는 PNG/JPEG 이미지 최소 3개와 대응 메타데이터를 데모 전에 준비한다.
- TIFF를 사용할 때는 원본을 수정하지 않은 PNG 파생본을 만들고 원천 sample ID, SHA-256과 변환 시각을 추적한다.
- 변환 시 픽셀 크기를 유지하며, 리샘플링하지 않은 경우에만 원천 `nm/pixel`을 재사용한다.
- 데모 사전점검은 파일 존재, 이미지 디코딩, 형식, 픽셀 크기, 양수 보정값과 manifest 무결성을 확인한다.
- 반복 시연을 위해 전용 PostgreSQL 데모 데이터와 런타임 업로드를 알려진 초기 상태로 되돌리는 절차를 제공하며 원천 샘플은 변경하지 않는다.

#### 4.6 5명·3일 독립 개발과 공통 발표

- **COL-001:** 다섯 명은 각자 소속 팀에 필요한 도구 하나를 독립 개발한다. NANoDB는 그중 한 프로젝트다.
- **COL-002:** 각 프로젝트 담당자는 자신의 요구사항, 구현, 데이터, 검증, 사용법과 시연을 책임진다. 기존 Role 1~5의 NANoDB 지원 분업은 폐기한다.
- **COL-003:** 각자 별도 작업 공간에서 개발하며 다른 네 명의 산출물을 NANoDB 완료의 필수 입력으로 두지 않는다.
- **COL-004:** 팀 공통 메시지는 `반도체 현업의 작은 도구를 AI로 더 빠르게 만들고, 검증하고, 다시 활용하게 한다`로 제안한다. 각 프로젝트의 실제 관련성을 설명하고 미확정 주제를 임의로 반도체 기능으로 포장하지 않는다.
- **COL-005:** NANoDB 일정과 중단 기준은 MVP 문서 9절의 3일 계획을 따른다. 다른 프로젝트는 각 담당자가 자신의 범위를 관리한다.
- **COL-006:** 매일 짧은 진행 공유와 상호 사용성 피드백을 권장하되 특정 팀원의 검토를 필수 완료 조건으로 두지 않는다.
- **COL-007:** 각 프로젝트는 `현업 문제`, `AI 개발에서 돕는 작업`, `실행 가능한 전후 비교`, `대회 후 사용자·활용 업무`를 같은 소개 형식으로 정리한다.
- **COL-008:** 각 담당자는 요구사항·주요 결정·구현·검증의 AI-DLC 연결 근거를 남긴다. 프롬프트 수나 코드 생성량만으로 효과를 주장하지 않는다.
- **COL-009:** 단일 서비스 제출 규정은 미확정이다. 제출 전 확인하고 필요하면 대표 서비스와 다른 결과물의 관계를 정리한다. 이번 요구사항은 공통 런타임·통합 로그인·다섯 도구의 기능 통합을 요구하지 않는다.
- **COL-010:** 발표에는 동작 완료 기능, 실제 AI 개발 검증 기록, 후속 비전을 구분한다. 각자 도구의 실행 방법과 알려진 한계를 남긴다.

담당자·프로젝트 목록은 각 주제가 확인된 뒤 팀 발표 자료에 기록한다. 미정인 네 프로젝트의 이름·역할·기능을 이 문서에서 생성하지 않는다.

- **DOC-006:** GitHub Actions는 `main` push와 수동 실행을 지원하고 VitePress build 성공 후에만 Pages artifact를 배포한다.
- **DOC-007:** 배포 workflow는 최소 권한인 `contents: read`, `pages: write`, `id-token: write`를 사용하고 `github-pages` environment를 지정한다.
- **DOC-008:** 동일 시점 배포는 하나만 진행하며 실행 중 배포는 중간 취소하지 않는다.
- **DOC-009:** `docs/.vitepress/cache`와 `docs/.vitepress/dist`는 Git에 커밋하지 않는다.
- **DOC-010:** 사이트에는 원본 이미지, 내부 감사 로그, 비밀정보 또는 공개 승인이 없는 데이터를 복제하지 않고 승인된 설명·축소 자산과 저장소 링크만 사용한다.
- **DOC-011:** 실제 Pages 배포는 `main`에서만 실행한다. 게시 전 production build를 검증하며 PR 작성·PR 전용 검증 workflow는 필수로 두지 않는다.
- **DOC-012:** GitHub 저장소 Settings의 Pages Source가 `GitHub Actions`여야 한다는 관리자 설정 절차를 문서화한다.
- **DOC-013:** 게시한 정적 자료를 로컬 앱의 실시간 데이터처럼 표현하지 않는다. 기능별 완료·미완료와 캡처 버전·시각을 표시하며, 공개 사이트에서 동료 PC의 localhost 앱으로 연결하지 않는다. Pages 접근 실패 시 동일 build의 로컬 preview로 소개할 수 있어야 한다.

#### 4.8 AI 심사와 참여자 상호 평가

- **EVL-001:** 사용자가 제공한 다음 배점을 그대로 사용한다. 근거는 실제 산출물과 관찰 결과이며 점수 보장이나 자체 추정 점수를 표시하지 않는다.

| AI 심사 항목 | 비중 | 준비할 근거 |
| --- | --- | --- |
| AI-DLC | 25% | 요구사항·범위 결정, 사용자 승인 기록, 계획 체크박스, 실행한 단계·생략 사유, 요구사항과 검증 결과 연결 |

| 사용성 | 15% | 처음 보는 동료가 다음 행동을 식별하는지 관찰한 결과, CTA·오류·빈 상태, 짧은 사용 순서 |
| 유지보수성 및 보안 | 10% | 실행 README, 의존성 고정, 입력 검증·파일 경로 제한·공개 자료 점검의 실제 결과, 운영 보안 제외 범위 |

- **EVL-002:** 각 근거에 요구사항 ID 또는 절, 산출물 위치, 확인한 commit 또는 작업본 버전, 확인 시각, 통과·실패·미검증 상태를 연결한다. 내부 audit 원문은 공개 사이트에 복제하지 않고 승인된 결정 요약만 제공한다.
- **EVL-003:** 30분 AI 심사용 내부 준비 순서는 0~5분 문제·목적, 5~13분 핵심 데모, 13~20분 AI-DLC·검증 근거, 20~25분 사용성·유지보수·보안·한계, 25~30분 재확인·질의 여유로 둔다. 이는 팀의 준비안이며 공식 심사 진행 방식으로 단정하지 않는다. 정적 문서만 읽어도 같은 근거를 찾을 수 있어야 한다.
- **EVL-004:** 참여자 상호 평가에는 소개 URL과 2~3분 읽기 순서(문제 → 목적 → 실제 기능 → 근거)를 제공한다. 투표·평점 수집 기능은 만들지 않는다. 공식 배점·제출 도구·AI 심사와의 시간 중첩 여부는 미제공으로 기록하고 동일 기준으로 가정하지 않는다.
- **EVL-005:** 앱은 기본적으로 로컬 접속으로 한정하고, 업로드 형식·용량·저장 경로와 좌표·보정값을 서버에서 검증하며, 비밀정보·비공개 자료가 공개 산출물에 없는지 확인한다. 해당 결과를 검증 근거에 남긴다. 로그인·권한·운영 보안 확장은 기존 제외 범위를 유지한다.

- **EVL-006:** MVP 문서 8.4절에 따라 동일 개발 과제에서 수작업 설명과 컨텍스트 사용을 비교한다. 자료 준비 시간, 추가 설명·수정 요청 메시지 수, 검증 통과 수/전체 수와 조건 차이를 기록한다. 소수 사례 관찰이며 향상·토큰 절감을 보장하지 않는다.
- **EVL-007:** 앱 완성과 외부 AI 개발 데모 실행 여부를 구분한다. 프롬프트, 입력 버전, 생성 코드, 실행 명령과 실제 검증 결과를 보존한다. 사전 실행 기록은 시각·버전과 녹화 여부를 표시하며 미실행 예시를 성과로 주장하지 않는다.
- **EVL-008:** 대회 주제는 `AI 기반 S/W 개발 혁신 서비스 만들기 (feat. AI-DLC)`이며 사내 AI 개발에 사용하는 서비스라는 사용자 제공 취지를 따른다. 반도체 관련성은 도메인 차별화이며 추가 공식 배점으로 간주하지 않는다. AI-DLC 사용 과정과 제품의 AI 개발 지원 가치를 각각 입증한다.

#### 4.9 개발 컨텍스트 내보내기

정식 기능·데이터 계약은 [MVP 요구사항](../../../requirements/nanodb-mvp-requirements.md)의 CTX-001~012와 8.4절을 따른다. 이미지 한 장과 저장된 전체 측정의 스냅샷을 `context.md`, `data.json`, `task.md`, `checks.json`으로 묶은 ZIP으로 제공한다. 각 측정에는 라벨과 메모가 함께 들어가며 별도의 도형 배열은 두지 않는다. 계약 버전은 `2.0`이다. 스키마·좌표계·단위·보정 규칙, 수동 미검토 참고 상태, 개발 요청과 기대 결과를 포함한다.

원본 이미지 바이너리·다른 이미지·내부 절대 경로·감사 로그는 포함하지 않는다. 제조 식별정보·원본 파일명·메모 포함을 사용자에게 알리고 외부 AI로 자동 전송하지 않는다. 측정 없음·누락 이미지·유효하지 않은 데이터·다운로드 실패를 검증한다. AI 도구 사용과 생성 코드 실행은 앱 외부의 수동 작업이다.

### 5. 비기능 요구사항 요약

- 최신 Chrome 또는 Edge에서 마우스 입력의 1280px 이상 데스크톱을 지원 범위로 한다. 태블릿·모바일 터치 측정과 다크모드는 지원하지 않는다고 명시한다.
- PostgreSQL과 단일 앱 호스트의 로컬 파일 저장소를 사용하며 외부 유료 서비스 없이 실행한다.
- 해커톤에서는 로컬 PostgreSQL을 사용하고 연결정보는 환경 설정으로 주입하며 스키마 변경은 migration으로 재현한다.
- 초기 사내 베타는 등록 사용자 약 1,000명을 목표로 하지만 동시 접속·동시 쓰기 수용량은 부하 시험 전까지 보장하지 않는다.
- 로컬 파일 저장소를 유지하므로 다중 앱 인스턴스와 고가용성은 초기 베타 범위에 포함하지 않는다.
- 이미지 크기는 최대 20MB, 데모 데이터는 100건 이하를 전제로 한다.
- 목록과 상세 화면은 데모 환경에서 2초 이내 표시를 목표로 한다.
- 입력 오류, 빈 상태와 **성공 결과**를 모두 텍스트로 설명하며 색상만으로 상태를 구분하지 않는다.
- 되돌릴 수 없는 삭제는 앱 안의 확인 절차를 거치고 함께 사라지는 파생 데이터 건수를 알린다.
- 홈의 SEM/TEM 구성과 등록 추이는 데모 규모(100건 이하) 전제의 클라이언트 집계이며, 규모가 커지면 서버 집계로 옮긴다.
- 홈 소개 영상은 외부 임베드를 쓰는 유일한 예외이며, 영상을 불러오지 못해도 홈의 나머지 내용을 읽을 수 있어야 한다.
- README에 1~2개 명령으로 실행하는 방법과 데모 순서를 기록한다.
- 원본 이미지와 저장된 측정 geometry 사이의 연결을 유지하고, 원본 파일을 직접 수정하지 않는다.
- 저장 좌표는 원본 이미지 범위 안에 있어야 하고 서버가 유클리드 거리와 `nm/pixel`로 측정값을 재계산한다.
- 시각 값은 ISO 8601로 저장하며 화면에는 기준 시간대를 명시한다.
- 새로고침 전후 저장 좌표는 각 끝점 1px 이내, 표시 측정값은 0.01nm 이내로 동일해야 한다.
- 최초 좌표 변환은 MVP 문서 8.1의 알려진 1000×800px 기준 이미지·500px 거리·0.2nm/pixel 사례로 별도 검증한다. 표시값은 셋째 자리에서 반올림하여 둘째 자리까지 표시한다.
- 서버 재시작 후에도 메타데이터와 측정 결과가 유지되어야 한다.
- 문서 production build는 경고나 깨진 내부 링크 없이 완료되어야 하며, GitHub Pages에서는 `/nanodb_mvp/` 하위 새로고침과 정적 자산 로딩이 성공해야 한다.

### 6. 제외 범위

- 인증, 권한, SSO, 역할별 검토·승인과 운영 보안
- 이미지 메타데이터 자동 추출과 대량 업로드
- Layout 등록·연계, Die·시편·관찰 방향의 상세 추적성
- 자유 윤곽(폴리곤) 라벨링, 관심 영역 관리, 라벨 검수, 라벨 버전과 자동 영상처리 (측정에 이름을 붙이는 측정 라벨링은 구현 범위)
- 저장된 측정의 좌표·항목 수정과 수정 이력 (라벨과 메모 수정은 포함)
- 측정과 분리된 화살표·원 도형과 그 편집 이력 (측정은 삭제 후 다시 그리기만 지원)
- 태블릿·모바일 터치 측정, 다크모드
- 사용자 정의 파라미터의 제안·승격·폐기 및 정의 버전 관리(CTX 데이터 계약의 schema_version 표기는 포함)
- Pitch, Curvature, Roughness와 6종 Hole 피처의 고급 계측 자동 계산
- Tool 계약·실행 이력·생존율
- 전체 온톨로지와 계보 그래프
- 고급 산포 분석, 월간 리포트, 사용자용 OpenAPI와 에이전트 스킬
- 앱 내 모델 호출·라우팅·토큰 계량·RAG·MCP·생성 코드 자동 실행. 로컬 컨텍스트 ZIP과 외부 AI 개발 도구를 통한 수동 검증은 포함
- 고가용성, 재해 복구, 클라우드 배포와 운영 관측성
- 문서 검색 커스터마이징, 다국어, 댓글, 방문 분석, 커스텀 도메인과 별도 CMS

### 7. 수용 기준

- 홈의 활성 CTA는 사용 흐름 섹션의 두 개뿐이며 모두 구현된 화면으로 이동한다.
- 미구현 기능은 실행 가능한 UI로 오인되지 않는다.
- 이미지 또는 측정 추가 후 홈 KPI와 기준 시각이 갱신된다.
- 홈의 모든 수치는 실측 KPI이며 표본 수와 집계 기준 시각을 함께 표시한다.
- 이미지 등록부터 두 점 측정, 저장, 새로고침 후 복원까지 동작하며 P0 전체 흐름이 깨끗한 로컬 환경에서 한 번 이상 검증된다.
- 복원된 측정은 원본 이미지의 동일한 위치와 연결되고 파라미터 종류, 값, 단위, 보정값 및 생성 시각을 확인할 수 있다.
- 잘못된 파일, 누락 값, 0 이하 보정값을 저장하지 않고 오류를 표시한다.
- TIFF를 등록하면 원본이 보존되고, 원본 픽셀 크기를 유지한 PNG 파생본으로 화면에 표시되며 저장 좌표가 1:1로 맞는다.
- 이미지·측정 삭제는 확인 절차를 거치고, 함께 사라지는 파생 데이터 건수를 사전에 알린다.
- 측정 화면에서 `nm/pixel` 보정값과 원본 픽셀 크기를 확인할 수 있다.
- 저장·삭제 성공을 텍스트로 확인할 수 있다.
- 측정 라벨과 메모가 개발 컨텍스트 ZIP의 각 측정에 포함되고 같은 스냅샷의 재현성이 유지된다.
- 집계값에는 표본 수를 함께 표시하며, 제한된 TEM 측정값을 Product/Lot/Wafer 전체의 대표값으로 표현하지 않는다.
- 요구사항 식별자는 중복되지 않고 Markdown 문서가 정상적으로 렌더링된다.
- 데모용 PNG/JPEG 최소 3개가 메타데이터와 함께 준비되어 사전점검을 통과한다.
- 새로고침 전후 좌표 차이는 각 끝점 1px 이내이고 표시값 차이는 0.01nm 이내다.
- 초기화와 서버 재시작 후 지속성 검증 절차가 README에 기록된다.
- 다섯 명의 독립 개발과 공통 소개 형식을 확인하며 NANoDB는 다른 네 명의 구현 지원 없이 실행·검증할 수 있다.
- CTX-001~012 및 MVP 문서 8.4절의 개발 지원 게이트를 통과한다. 효과 비교의 실패·무개선도 기록한다.
- 로컬 VitePress production build가 성공하고 소개·근거 두 페이지와 내부 링크가 동작한다. 프로젝트 이유·목적·실제 features를 처음 보는 동료가 찾을 수 있다.
- Pages workflow는 build 성공 후 `main`에서만 배포하고 최소 권한을 사용한다.
- 배포 후 프로젝트 Pages URL에서 스타일·로고·내부 링크가 `/nanodb_mvp/` base 아래 정상 동작한다.
- 여섯 AI 심사 항목의 비중 합계가 100%이고 각 항목에서 실제 증거 또는 미검증 상태를 확인할 수 있다. 상호 평가의 공식 배점은 임의로 추가하지 않는다.
- 평가 자료의 게시 여부와 로컬 fallback 확인 결과를 앱 P0 완료 여부와 별도로 기록한다.

### 7.1 타임박스 게이트

- P0 계측 기반: 등록·재열기·두 점 측정·저장·복원·실제 건수·오류·빈 상태·데모 데이터와 초기화
- P0 개발 지원: CTX-001~012, 외부 AI 생성 코드 검증과 비교 기록
- P1(구현 완료): 단일 검색어·종류 필터, 측정 삭제, 이미지 삭제, 항목별 건수·평균·최소·최대 UI
- P1(2026-09-08): 측정 라벨링과 ZIP 포함, 측정 화면 보정값·배율 표시, 확대·이동, 라벨·메모 수정, 성공 알림, 앱 내 확인 대화상자, 검색 결과 유지·건수 표시
- P2(2026-09-08 신규): 폼 인라인 오류·필수 표시, 좌표 직접 입력, 문서 타이틀, 건너뛰기 링크, 에러 경계·미정의 경로, 재시도, 로딩 자리 확보. **미구현이어도 데모 실패로 보지 않는다.**
- 1일차 기반, 2일차 개발 지원, 3일차 검증·문서·리허설을 목표로 한다. 기반 통과 후 CTX, 두 게이트 통과 후 P1 순서다.
- 3일차에는 새 범위를 추가하지 않는다. 미완료 P0와 결함 해결을 우선하며 실패한 개발 지원 게이트를 완료로 바꾸지 않는다.

### 9. 결과 요약

NANoDB는 구조와 측정 기준이 계속 변하는 반도체 개발 단계의 SEM/TEM/Layout 데이터를 측정 근거와 함께 축적하는 제품이다. 장기적으로 구조 파라미터 버전, 제조·시편 추적성, 이미지 간 연결, 검토·승인, 반자동 측정을 지원한다. 현재 3일 MVP는 이미지 등록, 두 점 수동 측정, 측정 geometry 보존과 실제 건수 집계를 기반으로 개발 컨텍스트 내보내기와 AI 분석 코드 생성·검증을 연결한다. 검색·삭제·항목별 평균은 시간이 허용될 때만 추가한다. TIFF 원천 샘플과 브라우저 지원 형식 사이에는 추적 가능한 PNG 파생 데이터 준비 절차를 둔다.
