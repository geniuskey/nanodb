# NANoDB 해커톤 User Stories

3일 해커톤의 P0 데모와 평가에 필요한 여정만 기록한다. P1 검색·삭제·항목별 평균과 장기 로드맵은 요구사항에 유지하되 이번 이야기에서는 제외한다.

## US-01 데모 상태 준비

**사용자 이야기**: 로컬 데모 사용자로서 승인된 샘플과 알려진 초기 상태를 준비해 반복 시연을 같은 조건에서 시작하고 싶다.

**인수 조건**:

- PNG/JPEG 샘플 최소 3개와 필수 메타데이터가 사전점검을 통과한다.
- TIFF 원천은 변경하지 않고 파생본의 출처와 변환 정보를 추적한다.
- 초기화는 런타임 DB와 업로드만 대상으로 하며 원천 샘플을 삭제하지 않는다.

**관련 요구사항**: DAT-001~007

## US-02 홈에서 가치와 시작점 확인

**사용자 이야기**: 로컬 데모 사용자로서 홈에서 NANoDB의 목적, 실제 데이터 현황과 다음 행동을 즉시 이해하고 싶다.

**인수 조건**:

- 브랜드, 세 가지 가치와 `Image → Measurement → Development Context` 흐름을 표시한다.
- 이미지·측정 수는 실제 저장 데이터와 기준 시각을 사용하고 빈 상태도 명확히 표시한다.
- 활성 CTA는 구현된 홈, 이미지 목록과 등록 흐름으로만 연결된다.
- 미구현 기능은 `준비 중` 또는 로드맵으로 구분한다.

**관련 요구사항**: HOM-001~015, HOM-021, HOM-023~031, SUM-001, SUM-003~005

## US-03 이미지 등록과 재열기

**사용자 이야기**: 로컬 데모 사용자로서 SEM/TEM 이미지와 최소 제조 정보를 등록하고 목록에서 다시 열고 싶다.

**인수 조건**:

- PNG/JPEG 한 장과 SEM/TEM, Product, Lot, Wafer, 양수 `nm/pixel`을 저장한다.
- 형식·용량·필수값 오류는 저장하지 않고 이유를 표시한다.
- 등록 후 측정 화면으로 이동하며 목록에서 최신순 정보와 측정 건수를 확인하고 다시 열 수 있다.
- 원본 파일은 직접 수정하지 않는다.

**관련 요구사항**: IMG-001~006, CAT-001~002, CAT-004~005

## US-04 두 점 측정 저장

**사용자 이야기**: 로컬 데모 사용자로서 이미지 위 두 점으로 CD, Depth 또는 Thickness를 측정하고 근거와 함께 저장하고 싶다.

**인수 조건**:

- 화면 크기와 무관하게 원본 이미지 좌표로 두 점과 거리를 계산한다.
- 선, 픽셀 거리와 nm 값을 저장 전에 표시하고 초기화할 수 있다.
- 서버가 유효한 좌표와 보정값으로 값을 재계산해 측정 당시 정밀도로 저장한다.
- 이미지 밖, 동일 지점 또는 유효하지 않은 보정값은 저장하지 않는다.

**관련 요구사항**: MEA-001~011

## US-05 측정 근거 복원

**사용자 이야기**: 로컬 데모 사용자로서 저장한 측정값을 다시 선택해 원본 이미지의 같은 위치와 연결된 근거를 확인하고 싶다.

**인수 조건**:

- 현재 이미지의 저장 측정을 최신순으로 표시하고 선택한 선을 강조한다.
- 새로고침과 서버 재시작 후에도 측정 좌표와 값이 유지된다.
- 복원 좌표는 각 끝점 1px 이내, 표시값은 0.01nm 이내로 동일하다.
- 값은 소수점 둘째 자리로 표시하되 저장 정밀도는 유지한다.

**관련 요구사항**: RES-001~004, RES-006, MEA-009~010

## US-06 개발 컨텍스트 내보내기

**사용자 이야기**: 로컬 데모 사용자로서 선택한 이미지와 저장 측정을 AI 분석 코드 개발에 전달 가능한 ZIP으로 내보내고 싶다.

**인수 조건**:

- 측정이 있는 이미지에서만 고정 파일명 `context.md`, `data.json`, `task.md`, `checks.json`을 담은 ZIP을 생성한다.
- 좌표계, 단위, 계산식, 수동 미검토 상태, 개발 요청과 기대 결과를 명시한다.
- 다른 이미지, 이미지 바이너리, 내부 경로, 감사 로그와 비밀정보를 포함하지 않는다.
- 포함 정보를 사전에 알리고 자동 외부 전송이나 앱 내 코드 실행을 하지 않는다.
- 잘못된 데이터나 실패를 성공 ZIP처럼 제공하지 않고 원본 데이터를 변경하지 않는다.

**관련 요구사항**: CTX-001~012

## US-07 외부 AI 개발 검증

**사용자 이야기**: 로컬 데모 사용자로서 내보낸 컨텍스트를 기존 AI 도구에 전달해 요약 코드를 만들고 실제 결과를 검증하고 싶다.

**인수 조건**:

- 앱 밖에서 생성 코드를 검토하고 로컬에서 실행해 `checks.json`과 비교한다.
- 프롬프트, 입력 버전, 생성 코드, 실행 명령과 실제 통과·실패 결과를 보존한다.
- 수작업 설명과 컨텍스트 사용의 준비 시간, 추가 요청 수와 검증 결과를 같은 과제로 비교한다.
- 효과가 없거나 실행하지 못한 경우도 그대로 기록하며 앱 기능 완료와 구분한다.

**관련 요구사항**: CTX-006~011, EVL-006~008, MVP 요구사항 8.4절

## US-08 평가 근거 확인

**사용자 이야기**: 해커톤 평가자로서 짧은 정적 자료에서 문제, 실제 기능, AI-DLC 근거, 검증 상태와 한계를 확인하고 싶다.

**인수 조건**:

- VitePress 소개와 근거 페이지 최대 두 개로 읽기 흐름을 제공한다.
- 여섯 심사 항목을 실제 산출물과 통과·실패·미검증 상태에 연결한다.
- 비공개 이미지, 비밀정보와 내부 감사 원문을 게시하지 않는다.
- GitHub Pages와 동일 build의 로컬 preview 중 하나로 자료를 열 수 있다.
- 구현 완료, 외부 AI 데모와 게시 상태를 각각 구분한다.

**관련 요구사항**: DOC-001~013, EVL-001~005

## INVEST 검토

| 기준 | 결과 |
| --- | --- |
| Independent | 각 이야기는 관찰 가능한 데모 결과를 가지며, 필요한 선행 순서는 요구사항의 P0 게이트로 관리한다. |
| Negotiable | 구현 기술은 고정하지 않고 사용자 가치와 결과만 정의한다. |
| Valuable | 모든 이야기가 로컬 데모 사용자 또는 평가자 가치에 연결된다. |
| Estimable | 화면·데모 단계 단위로 범위를 제한했다. |
| Small | 3일 MVP에서 독립적으로 구현·검증 가능한 크기로 묶었다. |
| Testable | 각 이야기에 체크리스트형 인수 조건과 요구사항 연결이 있다. |

## 범위 요약

- **포함**: P0 계측 기반, P0 개발 지원, 데모 데이터와 최소 평가 자료.
- **제외**: P1 검색·삭제·항목별 평균, 앱 내 AI 호출, 자동 측정, 인증·권한, 다른 네 프로젝트 통합과 장기 제품 기능.
