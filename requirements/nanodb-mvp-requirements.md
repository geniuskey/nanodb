# NANoDB 3일 해커톤 MVP 요구사항 정의서

> 문서 목적: 5명이 3일 동안 각자 소속 팀에 필요한 도구를 개발한다. 이 문서는 그중 NANoDB 담당자 한 명이 완성할 MVP 범위를 정의한다. 다른 네 명의 구현 지원을 일정에 포함하지 않는다.
> 범위 기준: 완성도 높은 하나의 핵심 흐름을 우선하며, 운영 환경 수준의 기능은 포함하지 않는다.

홈 탭의 메시지, 정보 구조, 실제값/예시값 구분은 [`home-tab-requirements.md`](./home-tab-requirements.md)를 함께 따른다. 두 문서가 충돌하면 이 문서의 3일 MVP 범위와 [`constraints.md`](./constraints.md)의 제외사항을 우선한다.

## 1. 프로젝트 개요

### 1.1 서비스 한 줄 정의

NANoDB는 `Nano Assets, Never orphaned Database`의 약자다. 반도체 SEM/TEM 이미지와 측정 근거를 축적하고, 이를 AI 기반 분석 소프트웨어 개발에 필요한 컨텍스트와 검증 데이터로 재사용하는 경량 웹 애플리케이션이다. 부제는 `데이터는 쌓이고, 툴은 이어진다.`다.

### 1.2 해결하려는 문제

- SEM/TEM 이미지와 측정 결과가 파일 폴더와 스프레드시트에 나뉘어 보관된다.
- 측정값만 남고 어떤 이미지의 어느 위치를 측정했는지 알기 어렵다.
- Product, Lot, Wafer 정보와 이미지 및 측정값을 함께 검색하기 어렵다.

- AI로 분석 스크립트를 개발할 때 데이터 형식, 필드 의미, 좌표계, 단위와 기대 결과를 반복 설명해야 한다. 이 설명 준비 비용과 해석 오류를 줄이는 것이 이번 MVP의 검증 가설이다.

### 1.3 MVP 핵심 가치

- 이미지, 제조 식별정보, 측정 위치, 측정값을 하나의 흐름으로 연결한다.
- 별도 데스크톱 도구 없이 브라우저에서 기본 치수를 측정한다.
- 저장한 결과를 다시 열었을 때 측정 위치와 값을 재현한다.
- 선택한 이미지의 데이터 계약·측정 사례·요청 템플릿을 내보내 AI 분석 코드 개발에 재사용한다.
- 개발 자료 준비 시간, 추가 설명·수정 요청 횟수와 검증 통과 여부를 관찰한다. 효과 향상을 사전에 보장하지 않는다.
- 홈 탭에서 `왜 필요한가 → 무엇을 하는가 → 실제 축적 수치 → 사용 흐름`을 한 번의 스크롤로 설명한다.

### 1.4 대표 데모 시나리오

1. 사용자가 PNG 또는 JPEG 형식의 SEM/TEM 이미지 한 장을 등록한다.
2. Product, Lot, Wafer와 이미지의 `nm/pixel` 보정값을 입력한다.
3. 등록된 이미지를 상세 화면에서 연다.
4. CD, Depth 또는 Thickness 중 측정 항목을 선택한다.
5. 이미지 위의 두 점을 차례로 클릭한다.
6. 시스템이 픽셀 거리와 보정값을 이용해 실제 길이를 계산한다.
7. 사용자가 측정 결과를 저장한다.
8. 이미지 상세 화면 또는 측정 목록에서 측정선, 값, 제조 식별정보를 다시 확인한다.
9. 측정이 있는 이미지 한 장을 선택해 개발 컨텍스트 ZIP을 내보낸다.
10. 기존에 사용 가능한 AI 개발 도구의 새 대화에 묶음과 요청 템플릿을 전달해 측정 항목별 요약 CSV 생성 스크립트를 만든다.
11. 사용자가 코드를 검토하고 로컬에서 실행하여 사전에 확정한 기준 결과와 비교한다. 코드 생성·실행은 NANoDB 외부의 개발 활동이다.

## 2. 사용자와 서비스 구성

### 2.1 사용자

- **측정·분석자**는 이미지와 수동 측정 근거를 축적한다.
- **분석 소프트웨어 개발자**는 컨텍스트를 내보내 기존 AI 개발 도구에서 코드를 생성하고 검증한다. 한 사람이 두 흐름을 수행할 수 있다.
- 로그인과 역할 구분 없이 모든 화면을 사용할 수 있다.
- 한 브라우저에서 로컬 또는 데모 서버에 접속하는 사용 환경을 전제로 한다.

### 2.2 주요 구성 요소

- **홈 화면**: 서비스 목적, 공개 근거, 실제 KPI, 핵심 사용 흐름과 진입 CTA
- **이미지 목록 화면**: 등록된 이미지 조회와 간단한 검색
- **이미지 등록 화면**: 이미지 파일, 제조 식별정보, 보정값 입력
- **측정 화면**: 이미지 표시, 두 점 측정, 결과 저장 및 조회
- **컨텍스트 내보내기**: 선택 이미지의 명세·데이터·개발 요청 템플릿을 로컬 ZIP으로 제공
- **서버**: 이미지와 측정 데이터 저장 및 조회
- **저장소**: 로컬 파일 디렉터리와 PostgreSQL 데이터베이스

## 3. 핵심 기능 요구사항

요구사항은 다음 두 등급으로 실행한다. 본 문서에 없는 기능은 해커톤 MVP 범위가 아니다.

- **P0 (Demo Gate)**: 계측 기반(IMG/CAT/MEA/RES/SUM/DAT)과 개발 지원(CTX) 두 게이트로 구성한다. 계측 기반을 먼저 검증하고 CTX를 구현한다. 두 게이트와 8.4절의 AI 개발 데모가 모두 통과해야 대회용 MVP 완료다.
- **P1 (사용자 가치 우선)**: 사용자가 앱에서 실제로 얻는 값을 키우는 항목이다. P0 통합 검증 이후 시간 순으로 구현한다. 미완료여도 핵심 데모 실패로 보지 않는다.
- **P2 (품질 다듬기)**: 접근성·복구 동선·표현 통일처럼 있으면 좋은 항목이다. **미구현이어도 데모 실패나 게이트 불통과로 보지 않는다.** 3일 타임박스에서는 P0 결함 해결이 항상 우선이다.

| 우선순위 | 요구사항 ID | 구현 상태 (2026-09-08 검토) |
| --- | --- | --- |
| P0 | IMG-001~008, CAT-001~002, CAT-004~007, MEA-001~011, RES-001~004, RES-006, SUM-001, SUM-003~005, DAT-001~007, CTX-001~012 | 구현 완료 |
| P1 | CAT-003, RES-005, SUM-002, ANN-001~004 | 구현 완료 |
| P1 | ANN-005~008, MEA-012~014, RES-007, CAT-008~009, UIX-001~002, UIX-008, HOM-040 | 구현 완료 (2026-09-08) |
| P2 | IMG-009~010, UIX-004~007 | 구현 완료 (2026-09-08) |
| P2 | UIX-003, UIX-009 | 미구현 (데모 실패 조건 아님) |

2026-09-08 개정: 구현됐지만 요구사항이 없던 기능(TIFF 파생본, 이미지 삭제, 도형 라벨링)과 요구사항만 있던 화면 항목을 정합화했다. 근거는 [ui-ux-review-2026-09-08.md](../aidlc-docs/inception/requirements/ui-ux-review-2026-09-08.md)다.

### 3.1 이미지 등록

**목적**: 분석 대상 이미지와 최소 제조 식별정보를 함께 저장한다.

**기능 요구사항**:

- **IMG-001:** 사용자는 PNG, JPEG 또는 TIFF 이미지 한 장을 선택해 등록할 수 있어야 한다.
- **IMG-002:** 등록 시 다음 정보를 입력할 수 있어야 한다.
  - 이미지 종류: SEM 또는 TEM
  - Product ID
  - Lot ID
  - Wafer ID
  - 보정값: 양수인 `nm/pixel`
- **IMG-003:** 원본 파일명과 등록 시각은 시스템이 자동으로 저장해야 한다.
- **IMG-004:** 이미지 파일, 이미지 종류, Product ID, Lot ID, Wafer ID와 `nm/pixel` 보정값은 필수값이어야 한다.
- **IMG-005:** 확장자만 보지 않고 실제로 디코딩 가능한 PNG/JPEG/TIFF인지 확인해야 한다. 파일 형식, 20MB 용량 제한 또는 보정값이 잘못된 경우 저장하지 않고 이해하기 쉬운 오류를 표시해야 한다.
- **IMG-006:** 등록 성공 후 해당 이미지의 측정 화면으로 이동해야 한다.
- **IMG-007:** 브라우저가 `<img>`로 직접 표시할 수 없는 형식(현재 TIFF)은 원본을 수정하지 않고 보존하며, 등록 시 화면 표시용 PNG 파생본을 만들어 이미지 서빙에 사용해야 한다. 원본은 계속 원천 데이터로 남는다.
- **IMG-008:** 표시용 파생본은 원본 픽셀 크기를 유지하고 리샘플링하지 않아야 한다. 저장 좌표가 원본과 파생본에 1:1로 매핑되어야 한다.
- **IMG-009 (P2):** 등록 폼은 필수 입력을 사용자가 알 수 있게 표시해야 한다.
- **IMG-010 (P2):** 입력 오류는 가능한 경우 해당 입력 근처에 표시하고, `aria-invalid`와 설명 텍스트를 연결하며, 제출 실패 시 첫 오류 입력으로 포커스를 옮겨야 한다.

**의도적인 단순화**:

- Product, Lot, Wafer는 별도 마스터 테이블이 아닌 이미지 레코드의 문자열로 저장해도 된다.
- 중복 이미지 검사, 파일 해시, 메타데이터 자동 추출은 수행하지 않는다.

### 3.2 이미지 목록 및 검색

**목적**: 등록한 이미지를 찾고 측정 화면으로 이동한다.

**기능 요구사항**:

- **CAT-001:** 등록된 이미지를 최신 등록순으로 표시해야 한다.
- **CAT-002:** 각 항목에 썸네일 또는 축소 이미지와 다음 정보를 표시해야 한다.
  - 원본 파일명
  - SEM/TEM 구분
  - Product ID
  - Lot ID
  - Wafer ID
  - 저장된 측정 개수
- **CAT-003 (P1, 구현 완료):** 하나의 검색어로 파일명, Product ID, Lot ID 또는 Wafer ID를 부분 일치 검색할 수 있어야 한다. SEM/TEM 종류 필터를 함께 제공한다.
- **CAT-004:** 목록 항목을 선택하면 해당 이미지의 측정 화면으로 이동해야 한다.
- **CAT-005:** 데이터가 없거나 검색 결과가 없을 때 빈 화면 대신 안내 문구를 표시해야 한다. 검색·필터로 0건인 경우와 등록 자체가 0건인 경우를 구분한다.
- **CAT-006:** 사용자는 목록과 측정 화면에서 이미지를 삭제할 수 있어야 한다. 삭제 전에 함께 사라지는 측정·도형 건수를 알리고 확인을 받아야 한다.
- **CAT-007:** 이미지 삭제는 파생 데이터(측정·도형) 행을 먼저 지우고 커밋한 뒤 저장 파일을 삭제해야 한다. 실패해도 DB 행이 없는 파일을 가리키는 상태를 만들지 않는다.
- **CAT-008 (P1):** 검색·필터를 다시 조회하는 동안에는 이전 결과를 유지하고 갱신 중임을 알려야 한다. 목록이 매 입력마다 사라지지 않아야 한다.
- **CAT-009 (P1):** 현재 검색·필터 조건의 결과 건수를 표시해야 한다.

### 3.3 이미지 표시와 두 점 측정

**목적**: 이미지 위의 측정 위치와 실제 길이를 연결한다.

**기능 요구사항**:

- **MEA-001:** 측정 화면에 이미지가 화면 영역 안에 비율을 유지해 표시되어야 한다.
- **MEA-002:** 사용자는 측정 항목을 `CD`, `Depth`, `Thickness` 중에서 선택해야 한다.
- **MEA-003:** 사용자가 이미지 위에서 시작점과 끝점을 차례로 선택할 수 있어야 한다.
- **MEA-004:** 두 점을 잇는 선과 양 끝점을 이미지 위에 즉시 표시해야 한다.
- **MEA-005:** 실제 길이는 다음 식으로 계산해야 한다.

  `실제 길이(nm) = 원본 이미지 기준 두 점 사이 픽셀 거리 × 보정값(nm/pixel)`

- **MEA-006:** 화면에 이미지가 축소 또는 확대되어도 좌표와 거리는 원본 이미지 크기를 기준으로 계산해야 한다.
- **MEA-007:** 저장 전 현재 측정선의 픽셀 거리와 계산된 nm 값을 표시해야 한다.
- **MEA-008:** 사용자는 저장 전 두 점을 다시 선택해 측정을 초기화할 수 있어야 한다.
- **MEA-009:** 측정 저장 시 다음 정보를 보존해야 한다.
  - 연결된 이미지 ID
  - 측정 항목
  - 시작점과 끝점의 원본 이미지 기준 X/Y 좌표
  - 픽셀 거리
  - 계산된 nm 값
  - 사용한 `nm/pixel` 보정값
  - 선택 입력 메모
  - 생성 시각
- **MEA-010:** 저장 성공 후 측정선과 값이 저장된 측정 목록에 즉시 나타나야 한다.
- **MEA-011:** 이미지 바깥 클릭, 동일 지점 선택, 유효하지 않은 보정값은 저장할 수 없어야 한다.
- **MEA-012 (P1):** 측정 화면에 해당 이미지의 `nm/pixel` 보정값, 원본 픽셀 크기와 등록 시각을 상시 표시해야 한다. 측정값의 신뢰 근거를 측정 중에 확인할 수 있어야 하기 때문이다.
- **MEA-013 (P1):** 사용자는 이미지를 확대하고 이동해 원하는 위치를 크게 보며 점을 지정할 수 있어야 한다. 배율과 무관하게 좌표와 거리는 원본 이미지 기준으로 계산한다(MEA-006 유지).
- **MEA-014 (P1):** 현재 배율에서 화면 1px이 원본 몇 픽셀에 해당하는지 표시해 사용자가 지정 가능한 정확도를 알 수 있어야 한다. 원본이 화면보다 크면 축소 상태에서 원본 1px을 지정할 수 없다는 사실을 숨기지 않는다.

포인터 장치를 쓰지 않는 측정 대안은 UIX-003을 따른다.

### 3.4 저장된 측정 결과 조회, 메모 수정과 삭제

**목적**: 측정값의 근거 위치를 다시 확인하고, 근거는 그대로 둔 채 설명만 보완한다.

**기능 요구사항**:

- **RES-001:** 현재 이미지에 저장된 모든 측정 결과를 최신순으로 표시해야 한다.
- **RES-002:** 각 결과에 측정 항목, nm 값, 픽셀 거리, 생성 시각, 메모를 표시해야 한다.
- **RES-003:** 저장된 결과를 선택하면 대응하는 측정선을 이미지 위에 강조해 표시해야 한다.
- **RES-004:** 페이지를 새로고침하거나 이미지를 다시 열어도 저장된 측정선이 같은 위치에 표시되어야 한다.
- **RES-005 (P1, 구현 완료):** 사용자는 잘못 저장한 측정 결과를 확인 절차 후 삭제할 수 있어야 한다. 원본 이미지는 그대로 남는다.
- **RES-006:** 측정값은 소수점 둘째 자리까지 표시하되, 저장 데이터는 계산 정밀도를 유지해야 한다.
- **RES-007 (P1):** 사용자는 저장된 측정의 메모를 수정할 수 있어야 한다. 좌표, 측정 항목, 픽셀 거리, 계산된 값과 사용한 보정값은 저장 후 변경하지 않는다. 측정 근거는 불변으로 두고 설명만 보완하기 위한 것이다.

저장 측정의 좌표·항목 수정과 수정 이력 관리는 이번 MVP 범위가 아니다(`constraints.md` 참조). 잘못 찍은 측정은 삭제 후 다시 측정한다.

### 3.5 요약 정보

**목적**: 등록 데이터가 축적되는 모습을 짧은 데모로 보여준다.

**기능 요구사항**:

- **SUM-001:** 홈 화면에 전체 이미지 수와 전체 측정 수를 표시해야 한다.
- **SUM-002 (P1, 구현 완료):** 측정값이 있는 경우 측정 항목별 건수, 평균값, 최솟값과 최댓값을 표시해야 한다.
- **SUM-003:** 데이터가 없는 항목은 0 또는 `측정 없음`으로 명확히 표시해야 한다.
- **SUM-004:** 각 집계에는 표본 수 `n`과 집계 기준 시각을 표시해야 한다.
- **SUM-005:** 실제 저장 데이터 KPI와 발표용 예시값 또는 공개 통계를 시각적으로 구분해야 한다.

요약 정보는 별도 분석 대시보드가 아니라 홈 화면의 작은 카드 또는 표로 구현한다. 집계가 없는 항목에 PDF의 예시 숫자를 실제값처럼 표시하지 않는다.

### 3.6 개발 컨텍스트 내보내기 (P0)

**목적**: 이미지·측정 데이터의 의미를 AI에 반복 설명하는 비용과 좌표·단위 해석 오류를 줄일 수 있는지 검증한다. 최소 범위는 이미지 한 장과 그 이미지에 저장된 전체 측정이다.

- **CTX-001:** 측정 화면에서 저장 측정이 한 건 이상인 이미지에 `개발 컨텍스트 내보내기`를 제공한다. 미저장 측정은 포함하지 않는다. 측정이 없으면 버튼을 비활성화하고 이유를 표시한다.
- **CTX-002:** 서버는 선택 이미지와 그 측정만 동일 시점의 스냅샷으로 내보낸다. 다른 이미지, 전체 DB, 내부 절대 경로, 비밀정보와 감사 로그를 포함하지 않는다.
- **CTX-003:** 결과는 UTF-8 텍스트 파일을 담은 ZIP 하나다. `context.md`, `data.json`, `task.md`, `checks.json`을 필수로 포함한다. 파일명은 고정하며 사용자 입력을 압축 경로로 쓰지 않는다. 이미지 바이너리는 MVP 묶음에서 제외하고 실제 이미지 확인은 앱에서 수행한다.
- **CTX-004:** `data.json`은 `schema_version`, `exported_at`, `image`, `measurements`를 포함한다. `image`에는 ID, 원본 파일명, SEM/TEM 구분, Product/Lot/Wafer, 픽셀 크기와 보정값을 포함한다. 각 측정에는 ID, image_id, 항목, 두 점 좌표, distance_px, 측정 당시 보정값, value_nm, 메모와 생성 시각을 포함한다. 저장된 도형이 있으면 `annotations`를 함께 포함하며 각 도형에 ID, image_id, 도형 종류, 두 점 좌표, 제품, Step, 측정 항목 명과 생성 시각을 담는다. 수치는 저장 정밀도를 유지하며 measurements와 annotations는 각각 ID 순으로 정렬한다. 도형을 포함하면서 `schema_version`을 올린다.
- **CTX-005:** `context.md`에는 모든 내보내기 필드의 타입·의미·필수 여부, CD/Depth/Thickness가 사용자가 선택한 항목이라는 점, 원본 좌상단 원점·오른쪽 X·아래쪽 Y 좌표계, 좌표 범위, 유클리드 거리와 nm 환산식, 측정 당시 보정값 사용, 표시 반올림 규칙을 명시한다. 도형을 포함하는 경우 화살표·원 두 종류의 좌표 의미(화살표는 시작점과 끝점, 원은 중심과 반지름을 정하는 가장자리 점)와, 도형은 사용자가 붙인 참고 라벨이며 계산된 측정값이 아니라는 점을 함께 설명한다. 앱이 물리적 경계를 자동 판별했다고 표현하지 않는다.
- **CTX-006:** `task.md`에는 data.json을 읽어 항목별 요약 CSV를 생성하는 개발 요청을 포함한다. 출력 열은 `parameter_type,count,mean_nm`이며 CD, Depth, Thickness 순으로 측정이 있는 항목만 출력한다. 저장 정밀도로 평균을 계산하고 표시만 소수점 둘째 자리로 반올림한다. 외부 서비스 호출은 요구하지 않는다.
- **CTX-007:** `checks.json`에는 저장 데이터에서 결정적으로 계산한 항목별 기대 건수와 반올림 전 평균, 검증 허용 오차 및 독립 합성 사례를 포함한다. 기준 사례는 1000×800px, (100,100)~(400,500), 0.2nm/pixel에서 500px·100nm다. 좌표·보정으로 계산을 확인하는 사례이며 이미지 경계 인식의 정답으로 쓰지 않는다.
- **CTX-008:** 묶음에 `measurement_method: manual_two_point`, `reference_status: unreviewed`를 명시한다. 수동 측정은 참고 데이터이며 계측학적으로 인증된 정답이나 Product/Lot/Wafer의 대표 표본이 아님을 설명한다. 합성 계산 사례와 실제 수동 측정을 구분한다.
- **CTX-009:** 내보내기 전 포함 필드와 제조 식별정보·파일명·메모가 포함된다는 사실을 보여준다. 사용자가 기존에 사용 가능한 AI 도구로 직접 전달하며 앱은 자동 업로드하거나 모델 API를 호출하지 않는다. 대회 시연에는 해당 AI 도구에 전달 가능한 합성 또는 승인된 데이터만 사용한다. 저장소 사용 승인이 외부 AI 전송 승인이라는 뜻은 아니다.
- **CTX-010:** 존재하지 않는 이미지, 저장 측정 없음, 유효하지 않은 좌표·보정·수치 또는 내보내기 실패는 이유를 표시하고 성공 ZIP처럼 전달하지 않는다. 내보내기는 원본 이미지나 저장 측정을 변경하지 않는다.
- **CTX-011:** 모델 선택·프롬프트 최적화·토큰 계량·코드 실행기는 앱 범위에 포함하지 않는다. README에는 압축 해제, 전달 파일, 개발 요청, 생성 코드 검토·로컬 실행·검증 순서를 기록한다. AI 도구를 쓸 수 없으면 과거 실행 기록으로 설명하되 live 실행 여부와 미검증 상태를 구분한다.
- **CTX-012:** 같은 스냅샷의 묶음은 exported_at과 ZIP 메타데이터를 제외한 데이터·명세·기대 결과가 같아야 한다. 도형을 포함한 뒤에도 같은 재현성이 유지되어야 한다. 도형을 포함하면서 계약 버전을 `1.0`에서 `1.1`로 올렸다. 한국어 메모와 특수문자가 JSON 파싱 및 압축 해제 후 보존되어야 한다. 내보내기 계약 버전은 명시하되 버전 관리 UI는 만들지 않는다.

### 3.7 도형 라벨링 (P1)

**목적**: 이미지 위 관심 위치를 화살표와 원으로 표시하고, 그 위치가 어떤 제품·Step의 어떤 측정 항목인지 이름을 붙여 남긴다. 두 점 측정이 "얼마인가"를 남긴다면 도형 라벨링은 "어디를 왜 봤는가"를 남긴다.

**기능 요구사항**:

- **ANN-001 (구현 완료):** 사용자는 측정 화면에서 화살표와 원 두 종류의 도형을 이미지 위에 그릴 수 있어야 한다.
- **ANN-002 (구현 완료):** 도형 좌표는 화면 배율과 무관하게 원본 이미지 기준으로 저장해야 한다. 도형은 이미지 범위를 벗어날 수 없다.
- **ANN-003 (구현 완료):** 도형마다 제품, Step, 측정 항목 명을 입력하고 저장할 수 있어야 한다.
- **ANN-004 (구현 완료):** 도형은 그린 순서대로 번호를 붙여 표에 한 행씩 표시하고, 같은 번호를 이미지 위 도형에도 표시해야 한다.
- **ANN-005:** 사용자는 잘못 그린 도형을 삭제할 수 있어야 한다. 원본 이미지와 저장된 두 점 측정에는 영향을 주지 않는다.
- **ANN-006:** 이미지 위 도형과 표의 행은 같은 강조 상태를 가져야 한다. 한쪽을 선택하면 다른 쪽도 함께 강조된다(RES-003과 같은 규칙).
- **ANN-007:** 도형은 두 점 측정과 별개의 참고 라벨이며 CD/Depth/Thickness 값을 만들지 않는다. 화면에서 계산된 측정값과 시각적으로 구분해야 한다.
- **ANN-008:** 도형과 라벨은 개발 컨텍스트 ZIP에 포함해야 한다(CTX-004, CTX-005). 라벨링 데이터만 AI 개발 컨텍스트에서 빠지지 않게 한다. 단, 도형은 계산값이 없으므로 `checks.json`의 기대 요약에는 포함하지 않으며 `task.md`는 도형을 무시하도록 명시한다.

**의도적인 단순화**:

- 자유 곡선·폴리곤 윤곽, 라벨 검수 상태와 라벨 버전 관리는 범위 밖이다(`constraints.md`).
- 도형은 그린 뒤 이동·크기 조절하지 않는다. 잘못 그린 도형은 삭제 후 다시 그린다.
- 제품·Step·측정 항목 명은 마스터 테이블 없이 문자열과 고정 선택지로 저장한다.

### 3.8 공통 UI/UX (UIX)

**목적**: 화면별 기능이 아니라 모든 화면에 걸치는 사용 경험을 한곳에 모은다. 5.1절의 공통 화면 원칙을 확인 가능한 항목으로 옮긴 것이다.

- **UIX-001 (P1):** 되돌릴 수 없는 동작(이미지·측정·도형 삭제)의 확인은 앱 안의 대화상자로 제공해야 한다. 함께 사라지는 파생 데이터 건수를 명시하고, 포커스를 대화상자로 옮기며, Esc로 취소할 수 있어야 한다.
- **UIX-002 (P1):** 저장·삭제·수정 성공을 텍스트로 알려야 한다(`role="status"`). 5.1절은 성공과 실패를 모두 텍스트로 표시하도록 규정하며, 실패(`role="alert"`)만으로는 이를 만족하지 않는다.
- **UIX-003 (P2, 미구현):** 포인터 장치를 쓰지 않는 측정 대안으로 시작점·끝점의 원본 좌표를 수치로 직접 입력해 측정을 만들 수 있어야 한다. 정밀 좌표 지정 수단도 겸한다. 현재 측정은 마우스 클릭 전용이며, 이 한계는 README의 알려진 제한에 기록한다.
- **UIX-004 (P2):** 화면마다 문서 타이틀을 갱신해 탭·히스토리·보조 기술에서 현재 화면을 구분할 수 있어야 한다.
- **UIX-005 (P2):** 헤더와 탭바를 건너뛰고 본문으로 이동하는 링크를 제공해야 한다. 링크는 포커스를 받기 전에는 보이지 않는다.
- **UIX-006 (P2):** 예상하지 못한 렌더 오류와 정의되지 않은 경로는 빈 화면이 아니라 복구 동선이 있는 화면으로 처리해야 한다. 내부 오류 상세는 노출하지 않는다. 렌더 오류 화면은 다시 시도를 제공해 새로고침 없이 회복할 수 있어야 한다.
- **UIX-007 (P2):** 조회 실패에는 새로고침 외의 다시 시도 동작을 제공해야 한다.
- **UIX-008 (P1):** 사용자에게 보이는 문구는 한국어로 통일하고, 빈 상태에는 원인과 다음 행동을 함께 적어야 한다.
- **UIX-009 (P2, 미구현):** 로딩 중에는 결과가 들어올 자리를 확보해 화면이 크게 밀리지 않게 해야 한다. 로컬 실행과 100건 이하 데모에서는 체감이 작아 후순위로 둔다.

P2 항목은 미구현이어도 데모 실패나 게이트 불통과로 보지 않는다. 3일 타임박스에서는 P0 결함 해결과 P1 사용자 가치가 먼저다. 2026-09-08 기준 UIX-003과 UIX-009만 미구현으로 남아 있다.

### 4.3 무결성 규칙

- 측정은 반드시 존재하는 이미지에 속해야 한다.
- 이미지가 삭제되는 기능은 제공하지 않는다.
- 측정값은 클라이언트가 전달한 값을 그대로 신뢰하지 않고 서버에서도 좌표와 보정값으로 다시 계산한다.
- 측정 생성 후 이미지의 보정값이 바뀌더라도 기존 측정에는 측정 당시 보정값과 결과를 유지한다.

### 4.4 데모 데이터 준비 계약

- **DAT-001:** 데모 시작 전에 브라우저가 직접 등록할 수 있는 PNG 또는 JPEG 이미지가 최소 3개 준비되어야 한다.
- **DAT-002:** 준비 이미지에는 최소 SEM/TEM 구분, Product ID, Lot ID, Wafer ID와 양수인 `nm/pixel` 값이 함께 제공되어야 한다.
- **DAT-003:** 저장소의 TIFF 원천 샘플을 사용할 경우 원본을 수정하지 않고 PNG 파생본을 만든다. 파생본은 원천 `sample_id`, 원천 SHA-256과 변환 시각을 추적할 수 있어야 한다.
- **DAT-004:** TIFF에서 PNG로 변환할 때 픽셀 너비와 높이를 유지하며, `nm/pixel` 값은 리샘플링이 없을 때만 그대로 사용한다.
- **DAT-005:** 데모 데이터는 `PROJECT_AUTHORIZED` 또는 그보다 명확한 사용 승인 상태여야 하며, 출처 상태가 불명확한 이미지는 시연에 사용하지 않는다.
- **DAT-006:** 데모 직전 사전점검은 파일 존재, 이미지 디코딩, 지원 형식, 픽셀 크기, 양수 보정값과 manifest 무결성을 확인해야 한다.
- **DAT-007:** 반복 시연을 위해 전용 PostgreSQL 데모 데이터와 런타임 업로드를 알려진 초기 상태로 되돌리는 절차를 README에 기록해야 한다. 초기화는 저장소의 원천 샘플을 삭제하거나 수정하지 않아야 한다.

### 4.5 값과 좌표 규칙

- 모든 저장 좌표는 원본 이미지 픽셀 좌표계에 두고 `0 <= x < pixel_width`, `0 <= y < pixel_height`를 만족해야 한다.
- 픽셀 거리는 유클리드 거리 `sqrt((end_x - start_x)^2 + (end_y - start_y)^2)`로 계산한다.
- 서버 계산값을 기준값으로 저장하고, `distance_px`와 `value_nm`은 유한한 양수여야 한다.
- 화면 표시값은 소수점 셋째 자리에서 반올림하여 둘째 자리까지 표시한다(예: 12.346nm → 12.35nm). 저장값은 반올림 전 정밀도를 유지한다.
- 시각 값은 ISO 8601 형식으로 저장하고 화면에서는 기준 시간대를 명시한다.

## 5. 화면 요구사항

### 5.1 공통

- 데스크톱 브라우저와 최소 1280px 너비의 해커톤 시연 화면을 우선한다.

- 처리 중에는 버튼 중복 클릭을 막고 진행 상태를 표시해야 한다.
- 성공과 실패 결과를 텍스트로 표시해야 하며 색상만으로 구분하지 않는다.

### 5.2 홈 화면

- 첫 진입 경로(`/`)는 홈이어야 한다.
- 상단에는 NANoDB 로고, 브랜드 확장명과 부제, 홈·이미지 목록·이미지 등록으로 이동하는 내비게이션과 실제 데이터 기준의 상태 요약을 표시한다.

- 개발 컨텍스트 내보내기 버튼, 포함 내용 안내와 오류 상태를 제공한다(CTX-001~012).

## 6. 최소 API 요구사항

구현 방식은 자유지만 프론트엔드와 서버를 분리한다면 다음 기능을 제공한다.

| Method | Path 예시 | 목적 |
| --- | --- | --- |
| `POST` | `/api/images` | 이미지와 메타데이터 등록 |
| `GET` | `/api/images` | 이미지 목록 및 검색 |
| `GET` | `/api/images/{id}` | 이미지 상세와 측정 목록 조회 |
| `GET` | `/api/images/{id}/file` | 이미지 파일 조회 |
| `POST` | `/api/images/{id}/measurements` | 두 점 측정 저장 |
| `DELETE` | `/api/measurements/{id}` | 측정 결과 삭제 |
| `GET` | `/api/summary` | 전체 및 항목별 요약 조회 |
| `GET` | `/api/images/{id}/context-export` | 선택 이미지 개발 컨텍스트 ZIP 다운로드 |

- 성공 응답과 오류 응답은 일관된 JSON 형식을 사용한다.
- 존재하지 않는 이미지 또는 측정 ID는 `404`로 응답한다.
- 입력값 오류는 `400` 또는 `422`로 응답하고 사용자가 수정할 수 있는 메시지를 제공한다.

## 7. 비기능 요구사항

### 7.1 실행 환경

- 로컬 PC에서 명령 1~2개로 실행할 수 있어야 한다.
- 별도 유료 서비스나 외부 API 없이 동작해야 한다. 홈 소개 영상만 예외로 외부 임베드를 사용하며, 이 경우에도 영상이 없으면 홈의 나머지 내용은 그대로 읽을 수 있어야 한다(HOM-040).
- 데이터베이스는 PostgreSQL, 이미지 저장소는 단일 앱 호스트의 로컬 디렉터리를 사용한다.
- 해커톤에서는 로컬 PostgreSQL을 사용하며 DB 연결정보는 환경 설정으로 주입하고 비밀값을 Git에 커밋하지 않는다.
- 스키마 생성과 변경은 새 환경에서 재현 가능한 migration으로 관리한다.
- 새 환경에서 실행 방법과 데모 순서를 README에 기록한다.

### 7.2 성능과 제한

- 최신 Chrome 또는 Edge에서 마우스 입력의 1280px 이상 데스크톱을 지원 범위로 한다. 태블릿·모바일 터치 측정과 다크모드는 지원 범위가 아니다.
- 홈의 SEM/TEM 구성과 등록 추이는 데모 규모(100건 이하) 전제로 목록 응답을 클라이언트에서 집계한다. 규모가 커지면 서버 집계로 옮긴다.
- 이미지당 최대 용량은 20MB로 제한한다.
- 목록과 상세 조회는 데모 데이터 100건 이하에서 2초 안에 표시되는 것을 목표로 한다.
- 해커톤 완료 기준은 데모 데이터 100건 이하와 단일 앱 인스턴스다.
- 초기 사내 베타는 등록 사용자 약 1,000명을 목표로 하지만 동시 접속·동시 쓰기 수용량은 부하 시험 전까지 보장하지 않는다.
- 로컬 파일 저장소를 유지하므로 다중 앱 인스턴스와 고가용성은 초기 베타 범위에서 제외한다.

### 7.3 안정성

- 업로드 파일명 충돌을 피하도록 내부 저장 파일명을 별도로 생성한다.
- 서버 재시작 후에도 이미지 메타데이터와 측정 결과가 유지되어야 한다.
- 예상하지 못한 서버 오류의 상세 스택을 사용자 화면에 노출하지 않는다.

## 8. MVP 완료 기준

### 8.1 P0 계측 기반 게이트

다음 시나리오가 깨끗한 로컬 환경에서 동작하면 계측 기반이 완료된다. 대회용 MVP 완료에는 8.4절 개발 지원 게이트도 필요하다.

- PNG/JPEG 이미지를 필수 메타데이터와 유효한 `nm/pixel` 값으로 등록할 수 있다.
- 등록한 이미지가 최신순 목록에 나타나고 다시 열 수 있다.
- 측정 화면에서 두 점을 선택하면 선, 픽셀 거리, nm 환산값이 표시된다.
- 측정을 저장한 뒤 새로고침해도 같은 좌표의 선과 값이 복원된다.
- 같은 이미지에 CD, Depth, Thickness 측정을 각각 한 건 이상 저장할 수 있다.
- 저장된 측정 한 건을 선택하면 대응하는 측정선이 강조된다.
- 이미지 수와 측정 수가 실제 저장 데이터와 일치한다.
- 잘못된 파일, 누락 입력, 0 이하 보정값에 대해 사용자에게 오류가 표시된다.
- 빈 데이터 상태에서도 화면이 깨지지 않는다.
- 홈의 KPI가 실제 저장 데이터와 일치한다. P1 공개 통계를 표시한다면 출처와 발표 연도를 함께 표시한다.
- 홈의 CTA가 구현된 화면으로 이동하고, 미구현 로드맵 항목은 실행 가능한 것처럼 보이지 않는다.
- README의 실행 절차를 따라 다른 사람이 로컬에서 실행할 수 있다.
- 데모용 PNG/JPEG 이미지 최소 3개와 대응 메타데이터가 준비되어 있고 사전점검을 통과한다.
- 같은 저장 측정을 새로고침 전후로 비교했을 때 각 끝점의 원본 좌표 차이가 1px 이내이고 표시 측정값의 차이가 0.01nm 이내다.
- 알려진 기준 이미지로 최초 좌표 변환 정확성도 검증한다. 1000×800px 이미지의 (100,100)과 (400,500), 보정값 0.2nm/pixel은 500px·100.00nm여야 한다. 100%와 50% 표시 크기 및 뷰어 여백이 있는 배치에서 같은 기준점을 선택하여 각 끝점 오차가 원본 기준 1px 이내인지 확인한다. 정확한 좌표를 서버에 입력한 계산 결과는 500px·100.00nm와 일치해야 한다. 수동 클릭 결과는 클릭 오차를 고려하여 100.00nm 대비 0.4nm 이내로 검증한다.
- 서버를 재시작한 뒤에도 등록 이미지와 측정이 조회된다.
- 데모 초기화 절차를 실행한 뒤 알려진 초기 데이터 건수로 돌아간다.

### 8.2 P1 확장 기준

- 단일 검색어로 파일명, Product ID, Lot ID 또는 Wafer ID를 부분 일치 검색한다.
- 저장된 측정 한 건을 확인 절차 후 삭제할 수 있다.
- 항목별 건수와 평균이 실제 저장 데이터와 일치하며 단위와 `n`을 표시한다.

P1 요구사항은 시간이 남을 때 추가하며, P0 출시 게이트를 불안정하게 만들면 제거하거나 비활성화한다.

### 8.3 검증 증거

- 최소 한 번의 P0 전체 흐름 실행 결과를 체크리스트로 남긴다.
- 자동화가 쉬운 거리 계산, 입력 검증, 서버 재계산과 집계는 테스트로 확인한다.
- 좌표 오버레이 복원은 데스크톱 브라우저에서 새로고침 전후를 직접 확인한다.
- 알려진 제한과 미완료 P1 항목은 README에 명시하며 동작하는 기능처럼 노출하지 않는다.

### 8.4 P0 개발 지원 게이트와 효과 검증

- CTX-001~012를 확인한다. ZIP의 필수 파일과 JSON 파싱, 선택 이미지 한정, 필드·값 보존, 수동 참고 상태, 오류와 빈 상태를 검증한다.
- 독립 기준 데이터는 CD 10nm·20nm, Depth 30nm로 준비한다. 요약은 CD 2건·15.00nm, Depth 1건·30.00nm이며 Thickness 행은 없어야 한다. 서버 내보내기와 AI 생성 스크립트 모두 이 기대 결과와 비교한다. CTX-007의 좌표 환산 사례도 별도로 확인한다.
- 생성 스크립트의 CSV 헤더·행 순서·건수는 정확히 일치해야 하며 평균 표시값은 기대 반올림 결과와 일치해야 한다. 반올림 전 계산값을 검증할 경우 절대 오차 0.000001nm 이하를 사용한다.
- 실제 내보낸 데이터로 AI 생성 코드의 검토·실행·검증을 최소 한 번 완료하고 프롬프트, 생성 코드, 실행 명령, 입력 버전과 결과를 근거로 남긴다. 사전 작성 코드를 AI 생성 결과로 소개하지 않는다.
- 비교는 같은 과제·원천 데이터·사용자, 가능한 한 같은 모델·설정의 새 대화에서 `수작업 설명 준비`와 `NANoDB 컨텍스트 사용`을 각각 최소 한 번 수행한다. 실행 순서, 모델명·확인 가능한 버전, 설정, 시각과 차이점을 기록한다.
- 자료 준비 시간은 원천 데이터가 준비된 상태에서 AI에 보낼 설명·파일 준비를 시작한 시점부터 최초 요청 전달 준비 완료까지다. 모델 대기·코드 실행 시간은 별도 기록한다. 최초 요청 이후 추가 설명·수정 요청 메시지 수와 동일 검증 사례 통과 수/전체 수를 기록한다.
- 비교는 소수 사례 관찰이며 유의미한 개선이나 토큰 절감을 완료 조건으로 요구하지 않는다. 개선이 없거나 실패해도 그대로 기록한다. 다만 생성 코드 검증이 통과하지 못하면 개발 지원 게이트는 미완료다.
- 앱 런타임과 내보내기는 오프라인 가능해야 한다. AI 생성 단계는 외부 개발 도구의 사용 가능성에 의존한다. 사전 실행 증거를 사용할 경우 버전·시각·녹화 여부를 표시한다. 실행 이력 없이 예시만 있는 경우 검증 완료로 표시하지 않는다.

## 9. 3일 구현 우선순위

| 일자 | 목표 | 완료 결과 |
| --- | --- | --- |
| 1일차 | 담당자별 독립 과제 확정; NANoDB 등록·계측·저장·복원 | 계측 기반 게이트 검증, 개발 컨텍스트 계약 확정 |
| 2일차 | 컨텍스트 ZIP 내보내기, AI 생성 코드 검증 | 개발 지원 게이트 실행, 비교 관찰과 실패 수정 |
| 3일차 | 재현성·효과 비교 확인, 최소 소개 자료와 리허설 | 실행 방법, 실제 기능·한계, AI-DLC 근거와 데모 확보 |

### 9.1 타임박스 중단 기준

- 1일차에 계측 기반이 통과하지 못하면 P1·공개 통계·시각적 개선을 제외하고 기반 오류를 먼저 수정한다.
- 계측 기반 통과 후 CTX를 구현한다. CTX는 대회 주제 연결에 필요한 P0이며 검색·삭제·UI 평균 카드보다 우선한다.
- 2일차 종료까지 내보내기와 AI 생성 코드 검증이 연결되지 않으면 P1을 모두 제외하고 3일차를 개발 지원 P0의 미완료 작업과 결함 해결에 사용한다.
- 3일차에는 새 범위를 추가하지 않는다. 최종 리허설 전 기능을 동결하고 실행·데이터·문서 상태를 맞춘다.
- 끝까지 CTX가 통과하지 못하면 계측 도구만 완료한 것으로 표시하고 대회용 MVP 완료라고 주장하지 않는다.
- 각자 소속 팀에 가져갈 실행 가능한 도구와 사용법을 남긴다. 다른 네 명의 구현·데이터·QA 지원을 NANoDB 완료의 필수 의존성으로 두지 않는다.

## 10. 결정 우선순위와 가정

### 10.1 충돌 해결 순서

문서나 시안이 충돌하면 다음 순서로 판단한다.

1. 이 문서의 P0 출시 게이트와 `constraints.md`의 명시적 제외 범위
2. 이 문서의 기능·데이터·비기능 요구사항
3. `home-tab-requirements.md`의 홈 화면 표현 요구사항
4. PDF 시안과 장기 제품 비전

### 10.2 현재 가정

- 5명이 각자 독립 도구를 3일간 개발한다. NANoDB 담당자가 자신의 앱·데이터·검증·문서를 책임진다. 팀 공통 발표와 상호 피드백은 COL 요구사항을 따른다.
- 앱·내보내기는 인터넷, 외부 계정과 외부 API 없이 가능해야 한다. 기존 AI 도구를 사용하는 생성 코드 데모와 GitHub Pages 게시에는 별도 연결이 필요할 수 있으며, 사전 실행 증거와 로컬 문서 preview를 준비한다.
- TIFF는 검증 가능한 원천 데이터이며, 브라우저 데모에는 원본을 보존한 PNG 파생본을 사용한다.
- 보정값은 manifest 또는 사용자가 알고 있는 값으로 입력하며, MVP가 scale bar에서 추론하지 않는다.
- 평균은 저장된 측정의 기술 통계일 뿐 Product, Lot 또는 Wafer 모집단을 대표한다는 의미가 아니다.
- 기술 스택 선택은 위 계약과 3일 제약을 만족하는 범위에서 Workflow Planning 단계에 확정한다.

### 10.3 평가용 문서와 심사 범위

- 대회 후 30분 AI 심사와 참여자 상호 평가를 위한 최소 VitePress 소개 자료를 별도 산출물로 둔다. 앱 기능이 아니며, 프로젝트가 만들어진 이유·목적·실제 features·데모·검증 근거·한계를 소개한다.
- 문서·협업·평가 요구사항의 기준은 `aidlc-docs/inception/requirements/requirements.md`의 COL, DOC, EVL 항목이다. 앱 P0/P1과 평가 자료 완료 여부를 별도로 기록한다.
- 사용자가 제공한 AI 심사 배점은 AI-DLC 25%, 문제 정의 및 해결 20%, 창의성 15%, 완성도 15%, 사용성 15%, 유지보수성 및 보안 10%다. 참여자 상호 평가의 배점·제출 방식은 미제공이며 AI 심사와 같은 배점으로 가정하지 않는다.
